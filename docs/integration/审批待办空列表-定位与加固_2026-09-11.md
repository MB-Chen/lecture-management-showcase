# 审批待办空列表 — 定位与加固（2026-09-11，v2 09:21）

> **场景 1**（已定性）：教学秘书账号（U-01）进「审批待办」页列表空 → **口径正确的空**（该账号当前无讲义待办），见 §结论 v1。
> **场景 2**（09:21 新增，🔴 **真 bug**）：**课程负责人**崔幸账号进同一页面，看不到自己的审批任务 —— 而流程中心明确显示「课程负责人审批 / 崔幸 / 未审核」，组表也有对应记录（`leader_id=U-03, audit_status=0`，即 id=11）。

## 🔴 结论 v2（09:21）：**设计缺陷 —— 把「按角色猜范围」当成了必经过滤**

`loadPendingTasks` 的**数据来源**被放在了「阶段 2：按角色查组表」这一层。而待办归属的**唯一权威**是流程引擎的 `getMyPendingTasks`（阶段 0/1）。

> **角色过滤只能当「优化」，不能当「必经」** —— 一旦角色解析失败/缺失（如课程负责人），源头就滤成 0 行，后面 `pendingMap` 匹配再准也无从发挥。

三种角色 → 空列表的路径（当前代码）：

| `resolvedRole` 实得 | 命中分支 | 查询条件 | 结果 |
| --- | --- | --- | --- |
| `LEADER` | LEADER（正确） | `leaderId = ${userId}` | 能看到自己的组 ✅ |
| **`TEACHER`**（负责人被判成教师） | TEACHER | `teacherId = ${userId}` | 负责人不是提交人 ⇒ **0 行 ⇒ 恒空** 🔴 |
| **空 / null / 大小写不符** | TEACHER（静默兜底） | `teacherId = ${userId}` | 同上 ⇒ **恒空** 🔴 |

### 为什么「课程负责人」大概率判不出来

任务书（`docs/讲义管理系统-CodeWave搭建任务书.md` §5.7）给 LEADER 定义了两条信号：

- **主信号**：`currentRole.businessRoleName == 'jygl_course_leader'`
- **副信号**：查教务 `tpm_approval_set WHERE task_user3 = userId AND is_delete = 0`

🔴 **主信号在本场景不可用**：「课程负责人」是**逐课程**的（`tpm_approval_set` 是 `course_code` 主键 1:1），而平台业务角色是**全局**的 —— 一个人可能负责 3 门课、也可能一门都不负责，**没法在业务角色管理里给每个负责人指派 `jygl_course_leader`**。

⇒ **LEADER 判定实际只能走副信号（查 `tpm_approval_set.task_user3`）**。若 `resolveRoleAndCollege` 实现时只做了 `businessRoleName → 角色` 的映射、没查 `tpm_approval_set`，则：

- 教秘/院长/处长 **正常**（靠全局业务角色就能判）→ 解释了 U-01 打进 `SECRETARY`；
- **课程负责人永远判不出** → 落 TEACHER → 待办页恒空。

⚠️ 另一处口径不一致的旁证：〈本地会话计划文件〉 写的判定表用的是**中文角色名**（`教师`/`教学秘书`/`教学院长`/`教务处处长`），而任务书写的是**英文 code**（`jygl_teacher`/`jygl_secretary`/…）。两种口径至少有一份是旧的 —— **`tpm_approval_set` 查询是否真的写进了 `resolveRoleAndCollege`，必须实测确认。**

### 方案 B′（根治角色链路；✅ 09:26 已拿到源码，可直接改）

        resolvedRole = 'SECRETARY';

    }

        resolvedRole = 'DEAN';
    } else {
    }
    if (businessRoleName == '教务处处长') {
        resolvedRole = 'DIRECTOR';

#### 🔴 第三轮（09:34）："先判教师、再判负责人" —— **顺序对，但判据层级错位**

主人的表述：**「教师的判断就是先判 `businessRoleId` 有没有值，再判 `userType` 是否 = 1」**。

**一、业务分层上完全正确**：课程负责人 ⊂ 教师（先得是个教师，才可能被指定为某门课的负责人），先判大类、再判小类，符合直觉。

**二、但这个"包含关系"不能变成"判据上的嵌套"** —— 因为两类判断的**数据源是正交的**：

| 判断 | 数据来源 | 性质 |
| --- | --- | --- |
| 是不是**教师** | `currentRole.businessRoleId` / `userType`（**平台角色变量**） | 平台侧、全局发放 |
| 是不是**课程负责人** | `TpmApprovalSet.taskUser3`（**教务表**） | 教务侧、逐课程指定 |

⇒ 「业务上包含」≠「判据上包含」。拿平台角色当前置门，只会造出一个漏斗：
**该账号只要被平台分配了任意业务角色（`businessRoleId` 非空）→ 连"是教师"都判不出来 → 连查表机会都没有 → `LEADER` 永远判不出**。这正是当前 bug 的机制。

**三、`userType` 是谁赋的值 —— ✅ 09:38 已澄清（主人问了同事）**

同事确认：**「先判 `businessRoleId` 有没有值、再判 `userType == 1`」就是平台判断"是否教师"的标准写法**。由此反推：

- `currentRole` 由**平台/登录侧注入**，`userType` 是平台给的账号类型（1=教师）⇒ ✅ **主人的改法（判断）才对**；
- 旧代码那句 `currentRole.userType = 1;`（**赋值**）因此**多余甚至有害** —— 它在"无业务角色"分支里把平台值硬写成 1，建议删（删前确认无其他逻辑依赖）；
- ✅ 该组合的语义可还原为：**`businessRoleId` 非空 = 有管理岗业务角色（秘书 / 院长 / 处长）；为空 + `userType==1` = 普通教师** —— 与"管理角色走中文名精确匹配"那段完全自洽。

🔴 **但这条信息同时还改变了对根因的排序：**

既然「普通教师」本来就该是**无业务角色**，而**崔幸（课程负责人）本质就是普通教师** ⇒ 他**大概率 `hasRoleId = false`** ⇒ **他能进查表分支** ⇒ 那么列表空的原因更可能是 ——

> **假设 B 升为第一嫌疑**：`leaderCheck = sql"SELECT COUNT(*) as cnt FROM TpmApprovalSet WHERE taskUser3 = ${userId}"` **一执行就崩**（`COUNT(*)` + 自定义别名 = 走聚合路径 = **幻影类型 `53724c75`**；且该分支在旧实现里**从不执行** ⇒ 实体名 `TpmApprovalSet` **从未跑通过一次**）⇒ `resolveRoleAndCollege` 抛错 ⇒ `created` 中断 ⇒ **列表空**。

> 反过来说：如果诊断打出 `hasRoleId=true`，那说明崔幸被配了某个业务角色（此时"教师门"才是元凶，走假设 A）。**两种情况都必须以诊断为准，但 B 现在更值得先排除。**
